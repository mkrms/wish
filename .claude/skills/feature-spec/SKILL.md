# feature-spec

Wish の機能仕様を、既存仕様と同じ構成で書くためのスキル。仕様は `implementer` と `tester` が
そのまま使える粒度（受け入れ条件まで）にすることが目的。

## 事前に読むもの
- `.claude/docs/wish-inventory.md`（その機能のフェーズ・位置づけ・現状の実装状態）
- 既存の `.claude/spec/feature/*.md`（フォーマットと用語の統一のため）
- 関連する `.claude/spec/infra/*.md` / `.claude/spec/design/README.md`（配布・分離・デザインの共通指針）
- 必要に応じて出典 `project/Wish.dc.html` と既存ソース（`src/types.ts` の型、対象コンポーネント）

## 保存先と命名
- `.claude/spec/feature/<kebab-case-name>.md`（例: `dashboard.md`, `capture-palette.md`）。
- 作成したら `.claude/spec/feature/README.md` の一覧に追記する。

## テンプレート（この構成で書く）
```markdown
# 機能仕様: <日本語名>（<英名スラッグ>）

## 目的
<この機能が何のために存在するか>

## スコープ（対象フェーズ）
- <含むもの / 含まないもの（将来拡張）を明確に>

## データ構造案
<src/types.ts の既存型（Task / Project / Memo / Settings / ParseResult）を前提とした案>

## 振る舞い
<状態遷移・アルゴリズム・UI フロー。箇条書きで具体的に。出典 Wish.dc.html の挙動を正とする>

## 受け入れ条件
- <テストで合否判定できる粒度の条件を列挙>

## 将来拡張（任意）
<後フェーズで足す予定の要素>

## 未決事項
<決め切れていない点。まとめて提示する>
```

## 原則
- **受け入れ条件はテスト可能に。** `tester` が `lib/` の純粋ロジックテストに落とせる粒度で書く。
- **ロジックと描画/入力/通信を分離**できる設計で記述する（純粋ロジックは `src/lib/` 前提）。
- データ構造は「案」とし、過度に実装を縛らない（既存ドメイン型を尊重）。
- **ダッシュボード系を書くときは、完了率・進捗率・フェーズを出さない方針（decisions-log D-005）を明記する。**
- 未決事項・要決定はまとめて列挙し、独断でスコープを広げない。
