# update-docs

Wish のドキュメントを、実態（コード・仕様・決定）と一致した状態に保つためのスキル。
ドキュメントは「あとから読む人（将来の自分・他エージェント）」のためのものであり、古い情報は
害になる。変更があったら速やかに同期する。

## ドキュメントの所在（どこを更新するか）
- `CLAUDE.md`（ルート）… プロジェクト概要のみ。基本変えない。
- `.claude/CLAUDE.md` … 開発ガイド・技術決定・禁止事項・ドキュメント構成。
- `.claude/docs/` … 設計ドキュメント・棚卸・意思決定ログ。
  - `wish-inventory.md` … スコープ棚卸（フェーズ付き）。
  - `decisions-log.md` … 重要判断の記録（ADR 的）。
- `.claude/spec/feature/` … 機能仕様。`.claude/spec/{infra,design,quality}/` … 機能外仕様。

## 手順
1. **何が変わったかを特定する。** 直近の実装・仕様変更・技術判断・スコープ変更を洗い出す。
2. **影響するドキュメントを列挙する。** 上記の所在から、更新が必要なファイルを選ぶ。
   - 機能の追加/変更 → 対応する `spec/feature/*.md` と、必要なら棚卸の該当行（状態 ✅/🟡/⬜ も更新）。
   - 技術選定・方針変更 → `.claude/CLAUDE.md` の決定事項 ＋ `decisions-log.md` に追記。
   - 構成・ルール変更 → `.claude/CLAUDE.md`。
3. **更新する。** 事実に合わせて本文を直す。決定は `decisions-log.md` に `D-XXX` 形式で追記
   （決定 / 背景 / 影響 を残す）。日付は会話の現在日付を使う（相対表現は使わず絶対日付に）。
4. **index とリンクを整える。** `spec/feature/README.md` の一覧、棚卸の「次のアクション」などを最新化。
   壊れた参照がないか確認する。
5. **差分を要約して報告する。** 何をなぜ更新したかを短くまとめる。

## 原則
- **重複を増やさない。** 同じ事実は 1 箇所に書き、他からは参照する。
- **古い記述は消す/直す。** 「残しておく」より「正す」。矛盾を見つけたら指摘する。
- ドキュメント更新自体はコミットしない（コミットは承認後・別途）。
